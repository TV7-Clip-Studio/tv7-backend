# TV7

## System Purpose
TV7 is a FastAPI service that turns long-form YouTube videos into ready-to-publish vertical shorts. An operator pastes a YouTube link, the system handles ingestion, AI highlight detection, automated clipping with stylized subtitles, and exposes the resulting assets for review, approval, and (stubbed) publishing. Everything lives inside this single application: API, background pipeline, storage metadata, and an internal admin dashboard.

## Core Domain Model
- **Video**
  - `id`: primary key.
  - `source_url`: original YouTube link.
  - `local_path`: filesystem or object-storage location of the downloaded full-length video.
  - `transcript_text`: full combined transcript/closed captions.
  - `status`: lifecycle state (`ingested`, `processing`, `ready`, `error`).
  - `created_at` / `updated_at`: timestamps.
- **Clip**
  - `id`: primary key.
  - `video_id`: foreign key to `Video`.
  - `start_sec` / `end_sec`: clip boundaries in seconds.
  - `local_path`: rendered 9:16 mp4 with subtitles burned in.
  - `caption_text`: hook/CTA text generated by the LLM.
  - `status`: lifecycle (`rendering`, `ready`, `published_partial`, `published_all`, `error`).
  - `created_at` / `updated_at`: timestamps.
- **PublishJob**
  - `id`: primary key.
  - `clip_id`: foreign key to `Clip`.
  - `platform`: target platform identifier (`youtube_shorts`, `tiktok`, `instagram`, etc.).
  - `status`: job state (`pending`, `success`, `error`).
  - `response_data`: JSON/text payload from the platform or stub.
  - `created_at`: timestamp.

These tables represent the single source of truth for processing state. Background workers should transition statuses atomically and leave audit trails when failures occur.

## Processing Pipeline
1. **Ingestion**
   - Endpoint `/videos/ingest` accepts `{ "youtube_url": "..." }`.
   - Creates a `Video` row (`status=ingested`) and enqueues the full pipeline.
   - `services/youtube_downloader.py` downloads the best-available video stream plus captions/transcripts, returning local file paths and transcript text.
   - Persist `local_path` and `transcript_text` on the `Video`.
2. **Highlight Detection**
   - `services/highlight_detector.py` sends the transcript to the LLM.
   - Response yields 3–5 segments with `{start_sec, end_sec, hook}`.
   - Creates `Clip` rows for each segment with `status=rendering` and stores the hook text in `caption_text`.
3. **Clip Rendering & Subtitle Styling**
   - `services/clipper.py` shells out to ffmpeg/ffprobe (configurable via `FFMPEG_BIN`/`FFPROBE_BIN`) to slice each segment, clamp durations to `CLIP_MAX_DURATION_SECONDS`, reframe to 9:16, and export mezzanine files before moving them into `/media/clips/{video_id}/{clip_id}.mp4`.
   - Portrait or ultra-tall sources narrower than 9:16 are automatically padded instead of cropped, preventing ffmpeg “input area out of bounds” failures while still producing 9:16 assets.
   - The Dramatiq `render_clips` stage fans out per-clip jobs keyed by a `render_batch_id`; each job runs the ffmpeg work in a background thread so multiple clips genuinely render in parallel, and once every clip reaches `ready` the system automatically enqueues `finalize_video`.
   - `services/subtitle_styler.py` (Phase 1.9) will overlay high-contrast subtitles sliced from the transcript segment.
   - Final assets saved to storage; update each `Clip` (`local_path`, `status=ready`).
4. **Video Completion**
   - When all clips reach `ready`, update the parent `Video.status="ready"`.
5. **Publishing (Stubbed)**
   - Endpoint `POST /clips/{clip_id}/publish` accepts `{ "platforms": [...] }`.
   - Creates `PublishJob` rows and (for now) marks them `success` immediately with a fake `posted_at`.
   - Update `Clip.status` (`published_partial` or `published_all` depending on coverage).

The pipeline must execute outside the request/response loop (Celery/RQ/Dramatiq/background tasks). Failures should set the relevant status to `error` and surface diagnostic information for operators.

## API Surface
- `POST /videos/ingest` — queue processing for a YouTube URL. Returns `{ "video_id": ..., "status": "queued" }`.
- `GET /status/{video_id}` — poll overall video status plus per-clip progress snapshots.
- `GET /videos/{video_id}/clips` — list generated clips with timing, caption text, preview URLs/paths, and status.
- `POST /clips/{clip_id}/publish` — create `PublishJob` records and trigger (stubbed) publishing automation.
- `POST /videos/ingest` — accept a YouTube URL, persist the `Video` row (`status=ingested`), and enqueue the background pipeline.
- `GET /admin/videos` — HTML dashboard of videos, statuses, and navigation to detail view.
- `GET /admin/videos/{video_id}` — HTML per-video view showing clip previews, metadata, and publish buttons hooked to the publish endpoint.
- All admin-prefixed routes require HTTP Basic auth; credentials are supplied via `ADMIN_USERNAME`/`ADMIN_PASSWORD` environment variables.

All endpoints remain within the FastAPI application. Swagger `/docs` should describe request/response contracts for the JSON APIs; admin routes can remain simple HTML templates for internal use.

## Operational Notes
- **Storage:** Local disk works for development; abstract via settings so object storage (S3, GCS) can be introduced later.
- **Background Execution:** Use a task queue (e.g., Dramatiq, RQ, Celery) or FastAPI `BackgroundTasks` wrapper that delegates to worker processes. Never block the ingest request on downloading or rendering.
- **Queue Implementation:** The current build uses Dramatiq with Redis. The API enqueues actors that run in a separate worker process (`scripts/run_worker.py`) which now stays alive until it receives SIGINT/SIGTERM. Make sure `DRAMATIQ_BROKER=redis` is configured and keep one worker process running (`make worker` locally, Fly `worker` group) so pipeline jobs are consumed. Redis connection strings live in settings and can be swapped for a stub broker during testing.
- **Inline dev mode:** When `DRAMATIQ_BROKER=stub`, the API executes the entire pipeline inline after ingest. This makes local/UI smoke tests deterministic—videos march from `ingested` → `processing` → `ready` without a worker—but should never be used in production.
- **Observability:** Record timestamps and durations per pipeline stage; expose them via logs and metrics to surface bottlenecks (download time, LLM latency, ffmpeg performance).
- **Admin credentials:** Rotate the HTTP Basic credentials via `make admin-credentials` (writes to `.env`, syncs Fly secrets, and prints the values) before deploying.
- **Extensibility:** Additional services (thumbnail generation, branded overlays, true publisher integrations) should build atop these core models without splitting the codebase.

## Media Storage & Rendering Workspace
- **Directory contract:** All media lives under `MEDIA_STORAGE_DIR` (default `./media`). Each video owns:
  - `media/videos/{video_id}` — original download + transcripts (`Video.local_path`, `Video.workspace_root`)
  - `media/clips/{video_id}` — final rendered shorts exposed via `/media/clips/{video_id}/{clip_id}.mp4`
  - `media/tmp/{video_id}/{clip_id}` — per-clip scratch space with `mezzanine/` and `subtitles/` children used during ffmpeg + captioning.
- **Workspace helper:** `app.services.render_workspace.VideoWorkspace` ensures this layout exists, returns deterministic public URLs, and exposes `ClipPaths` objects containing final, mezzanine, and subtitle file locations plus cleanup helpers. Rendering tasks should call `get_video_workspace(video_id)` once and reuse the returned paths instead of hard-coding directories.
- **Database metadata:** `Video.workspace_root` stores the absolute source directory, `Video.render_batch_id` tracks the active fan-out batch, and each `Clip` records `render_width`, `render_height`, `frame_rate`, `file_size_bytes`, and optional `thumbnail_path`. This keeps admin/API responses in sync with whatever the clipper produces (ffmpeg, remote worker, etc.).
- **Configuration knobs:** `CLIP_MAX_DURATION_SECONDS`, `CLIP_TARGET_HEIGHT`, and `CLIP_OUTPUT_BITRATE` live in `settings` to keep rendering parameters centralized. Future storage backends (S3/GCS) only need to swap `MEDIA_STORAGE_DIR` + StaticFiles mounting logic while the rest of the code continues to ask the workspace helper for paths/public URLs.
- **Rendering binaries:** `FFMPEG_BIN` and `FFPROBE_BIN` point to the host binaries (Docker image installs ffmpeg already). Local developers running outside Docker must install ffmpeg/ffprobe or override the paths in `.env`.

## API Layering & Dependencies

All FastAPI endpoints follow the same structure to keep concerns isolated and testable:

1. **Router (e.g., `src/app/api/v1/videos.py`)** – Validates request payloads, injects dependencies, converts domain objects into Pydantic response schemas, and translates service exceptions into HTTP errors. Routers never talk to the database directly.
2. **Dependencies (`app/deps/*.py`)** – Provide shared helpers for wiring infrastructure into routes. For example `app.deps.db.get_session` yields an `AsyncSession`, while `get_video_repository` instantiates repositories bound to that session.
3. **Repositories (`app/repositories/*.py`)** – Thin wrappers around SQLAlchemy queries and persistence helpers. They expose methods such as `get_by_source_url` and `add_and_refresh`, keeping ORM knowledge in one place.
4. **Services (`app/services/*.py`)** – Contain domain logic and orchestration (validation, logging, queue dispatch). Services return ORM instances or DTOs and are unaware of FastAPI specifics.
5. **Security (`app/deps/security.py`)** – Supplies `require_jwt_user`, a bearer-token dependency that validates JWTs (signed via `app/core/jwt.py`) and injects the current user. Swagger is configured to persist the bearer token for interactive testing.

When implementing a new endpoint:

- Add or reuse repository/service functions instead of embedding logic inside the router.
- Extend `app/deps` with new dependency constructors if the route needs extra collaborators.
- Convert ORM results to response schemas at the router boundary (`UserRead.model_validate(user)`), preserving strong typing for FastAPI.

See `docs/testing.md` for how these layers map onto the test strategy (unit, system, integration).
